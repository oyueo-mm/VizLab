# VizLab v1.1 — 성능 측정

## 1. 환경과 한계

- Chromium(Playwright, 헤드리스), 개발용 PC 한 대. 3,000노드 측정은 **프로덕션 빌드(`vite preview`)에서 각 설정을 5회 돌린 중앙값**입니다(v1.0은 1~2회였습니다).
- 헤드리스 Chromium은 소프트웨어 렌더링(SwiftShader)이라 실제 GPU·실기기 값이 아닙니다. 모바일 수치는 Pixel 7 **에뮬레이션**(뷰포트·배율)이며 실기기 값이 아닙니다.

## 2. 3,000노드 네트워크의 잔여 롱태스크

v1.0 문서의 ‘롱태스크 20개, 최대 약 200 ms’는 한두 번의 측정값이었고, 이번에 같은 구조(Worker + LOD, 코드 변경 없음)를 5회 반복한 중앙값은 다음과 같아 **그 값이 재현되지 않았습니다**(측정 편차가 큼).

| 노드 | 첫 그리기 | 레이아웃 종료 | 레이아웃 중 프레임 평균/p95/최대(ms) | 롱태스크(수/최대 ms/100 ms 초과) | 힙 |
| --- | --- | --- | --- | --- | --- |
| 1,000 | 50 ms | 2.57 s | 24.6 / 50 / 66.8 | 12 / 82 / 0 | 21 MB |
| 3,000 | 62 ms | 7.3 s | 24.2 / 50 / 66.7 | 4 / 80 / 0 | 26 MB |

- CPU 프로파일(개발 서버, 3,000노드, 샘플링 0.5 ms): 레이아웃 구간에서 JS 함수 시간은 `draw`가 약 460 ms뿐이고 나머지 약 8 s는 `(program)`(브라우저 내부 캔버스 래스터·합성)이었습니다. JS에서 줄일 만한 핫스팟은 남아 있지 않았습니다.
- 시도: 그리기 비용에 따라 그릴 링크 비율을 조절하는 **적응형 LOD**와 화면 밖 링크 생략을 넣고 같은 방식으로 5회 측정했습니다. 3,000노드에서 레이아웃 프레임 최대 66.7 → 100 ms, 롱태스크 최대 80 → 105 ms로 **개선되지 않아** 되돌렸습니다(코드에 남기지 않음).
- 10,000노드는 **측정하지 못했습니다**(네트워크 데이터셋의 노드 수 슬라이더 상한이 3,000).
- OffscreenCanvas·위치 전송 최적화 등은 시도하지 않았습니다. 위 프로파일이 JS가 아닌 래스터에 시간이 쓰임을 보여 주므로 우선순위가 낮다고 판단했을 뿐 검증한 결론은 아닙니다.
- Worker 응답성과 계산 속도: Worker 이전은 메인 스레드가 막히지 않게 한 것이며 d3-force의 계산 속도 자체를 빠르게 한 것이 아닙니다.

## 3. 3D: Canvas 2D와 WebGL 비교 (실제 측정)

같은 물결 곡면 메쓰(삼각형 N개)를 매 프레임 회전시켜 그렸습니다. Canvas 2D는 앱과 같은 방식(깊이 정렬 후 다각형 채우기), WebGL은 깊이 버퍼를 쓰는 평면 음영 셰이더입니다. 프레임 간격의 중앙값(p95), 단위 ms, 90프레임(큰 메쓰는 40프레임).

| 삼각형 | Canvas 2D (데스크톱) | WebGL (데스크톱) | Canvas 2D (모바일 에뮬레이션) | WebGL (모바일 에뮬레이션) |
| --- | --- | --- | --- | --- |
| 2,048 | 16.7 (17.8) | 16.6 (17.8) | 16.7 (17.7) | 16.7 (17.7) |
| 10,082 | 17.6 (19.1) | 16.7 (17.6) | 17.2 (19.7) | 16.6 (17.7) |
| 39,762 | 58.2 (77) | 16.4 (18) | 57.3 (66.4) | 16.5 (18.3) |
| 160,178 | 248.8 (278.9) | 47 (51.9) | 237 (268.5) | 46.4 (47.8) |

- WebGL 렌더러는 두 환경 모두 SwiftShader(소프트웨어)였습니다. 실제 GPU에서는 WebGL이 더 빠르고, 하드웨어 가속 Canvas 2D도 달라질 수 있습니다. 모바일 열은 에뮬레이션이라 실기기 값이 아닙니다.
- 앱의 3D 실험실에서 궤도 회전(드래그) 중 프레임: 등치면(삼각형 2,884), 파이버 곡면(3,624), 스트림 서피스(796), 스트림튜브, 하이퍼스트림라인, 스트림 리본, 행렬 큐브(칸 918), 토폴로지컬 랜드스케이프, 3D 지형, 3D 곡면 **모두 중앙값 16.7 ms, p95 16.8 ms(60 fps)**.
- 결론: 삼각형이 약 2만 개를 넘으면 WebGL이 확실히 낫지만(40,000개에서 약 3.5배, 160,000개에서 약 5배), **앱의 기본 실험실은 모두 4천 개 이하**라 현재 Canvas 2D로 충분합니다. 큰 격자 크기에서의 앱 내 삼각형 수는 측정하지 못했습니다(3D 실험실에는 데이터 크기 슬라이더가 없었습니다). 그래서 **WebGL을 도입하지 않았고** 기존 Canvas 구현을 유지했습니다. 이는 ‘평가를 수행했고 채택하지 않음’입니다.
