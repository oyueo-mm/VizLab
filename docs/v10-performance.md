# VizLab v1.0 — 성능 측정과 개선

## 1. 측정 환경과 한계

- 측정 도구: Playwright로 구동한 Chromium(헤드리스), 개발 서버(vite dev)와 `preview` 빌드가 섞여 있다. 한 대의 개발용 PC에서 **각 설정을 1~2회씩** 잰 값이다. 평균이 아닌 단일 실행이므로 ±수십 % 오차가 있을 수 있고 실제 사용자 기기(저사양 모바일 등)의 값이 아니다.
- 측정 항목: 노드 수 갱신 후 첫 그리기까지의 시간, 레이아웃이 끝나기까지의 시간(`data-running`이 0이 될 때까지), 레이아웃 중 프레임 간격(rAF), 100 ms 넘는 롱태스크 수, 휠·호버 중 프레임 간격, JS 힙.
- ‘Worker 응답성 vs 계산 속도’: Worker로 옮긴 것은 **메인 스레드가 막히지 않게 한 것**이지 d3-force의 계산 자체를 빠르게 한 것이 아니다. 레이아웃 계산 시간은 기준과 비슷하거나 더 걸릴 수 있고, 개선된 것은 레이아웃 도중의 입력 응답과 프레임 간격이다.

## 2. 3,000노드 네트워크 (before / after)

기준은 v0.9의 구현(메인 스레드에서 d3-force 시뮬레이션 틱을 돌리고 캔버스로 그림)이다.

| 노드 수 | 단계 | 렌더러 | 첫 그리기 | 레이아웃 종료 | 레이아웃 중 프레임(평균/p95/최대, ms) | 롱태스크(수/최대/100ms 초과) |
| --- | --- | --- | --- | --- | --- | --- |
| 100 | 기준 | svg | 106 ms | 4.7 s | 16.9 / 16.8 / 66.6 | 1 / 60 / 0 |
| 1,000 | 기준 | canvas | 339 ms | 10.5 s | 29.9 / 66.7 / 216.7 | 10 / 133 / 2 |
| 3,000 | 기준 | canvas | 882 ms | **26.0 s** | 101.5 / 183.4 / **666.6** | 29 / **470** / 9 |
| 3,000 | LOD 중간 단계 | canvas | 60 ms | 4.4 s | 27.4 / 50.1 / 83.3 | 5 / 83 / 0 |
| 1,000 | Worker + LOD | canvas | 63 ms | 2.6 s | 21.4 / 50.0 / 83.4 | 1 / 89 / 0 |
| 3,000 | Worker + LOD (최종) | canvas | 55~57 ms | **4.4~4.6 s** | 48~51 / 83.3 / 183.3 | 20~21 / 197~199 / 1 |

해석(정직하게):

- 기준의 병목은 **메인 스레드의 레이아웃 틱**(레이아웃 중 프레임 최대 667 ms, 롱태스크 470 ms)이었다. 렌더링(캔버스 그리기) 자체보다 레이아웃 계산이 지배적이었다.
- 최종 구조에서 3,000노드의 첫 그리기는 882 ms → 약 55 ms, 레이아웃 종료는 26.0 s → 약 4.5 s, 레이아웃 중 최악 프레임은 667 ms → 183 ms로 줄었다.
- ‘LOD 중간 단계’ 행은 Worker 도입 전에 링크 간략화(LOD)와 첫 동기 레이아웃 생략만 적용한 상태로 기억하지만, 이 행의 정확한 코드 상태를 기록해 두지 못했다. 이 행은 참고로만 읽어야 한다. 최종 값은 Worker 행이다.
- Worker 최종에서도 롱태스크가 20개 남는다(최대 약 200 ms). 이는 위치 데이터를 받아 3,000개 노드를 다시 그리는 메인 스레드 작업이며 완전히 없애지 못했다.
- 휠·호버 중 프레임 간격은 모든 설정에서 약 16.7 ms(60 fps)였다(레이아웃이 끝난 뒤의 상호작용).
- **10,000노드는 측정하지 못했다.** 네트워크 데이터셋의 노드 수 슬라이더 상한이 3,000이라 UI로 10,000을 만들 수 없었고, 상한을 올려 측정하는 작업은 하지 않았다.

## 3. 적용한 개선

1. `src/stats/netsim.worker.ts`: 캔버스로 그리는 큰 그래프(노드 400개 초과)의 d3-force 시뮬레이션을 Web Worker로 옮겼다. 메인 스레드는 위치를 받아 rAF로 묶어 그리기만 한다. 드래그·고정·일시정지는 Worker로 메시지를 보낸다.
2. 레이아웃 중 이동 시 링크 간략화(LOD): 링크가 4,000개를 넘으면 움직이는 동안 링크를 3개 중 1개만 그린다.
3. 링크별 메타 데이터 사전 계산, Worker 사용 시 첫 동기 레이아웃 생략.
4. 번들 분리: React·react-dom을 `react-vendor` 청크로 나눴다(아래 5절).

## 4. 3D 렌더링 / WebGL 평가

이번 버전에서는 3D 렌더링을 WebGL로 바꾸는 평가를 **수행하지 않았다.** 측정 가능한 이득이 확인되지 않으면 채택하지 않는다는 원칙에 따라 기존 캔버스 3D를 유지했다. 이 항목은 ‘평가를 하고 채택하지 않음’이 아니라 ‘평가를 하지 못함’이다.

- 메인 청크가 600 kB 경고 기준 아래로 내려왔다. 그러나 **첫 방문의 총 전송량은 줄지 않았고 약 9 kB 늘었다**(요청 하나 추가). 얻은 이득은 재방문 캐시(React는 배포마다 바뀌지 않으므로 다시 받지 않음)이다.
- 새 기법의 코드(차트·엔진·콘텐츠·데이터)는 모두 지연 로딩 청크다: v10 설명 68.6 kB, infoCharts10 31.7 kB 등. 홈의 신규 10단계 엔진도 별도 청크다.
- 메인 청크가 v0.9 대비 커진 부분(+19 kB)은 카탈로그 메타 데이터(20개 항목)와 홈 단계 목록이다. 카탈로그 메타데이터를 지연 로딩하지는 않았다.
